| Статус платежа не фиксируется при тайм-ауте шлюза | INT-001 (Blocker): при тайм-ауте деньги списываются, статус платежа не фиксируется. SD-004: тестовое приложение при оплате висит десять секунд и выдаёт ошибку. SD-009: двойное списание денег. | Пациент платит, а запись не подтверждается, или платит повторно. | Нет идемпотентности при создании записи | INT-005 (Blocker): дубли записей при повторных POST. SD-003: пациент дважды нажал «Записаться», образовались две записи. INT-010: идемпотентность внесена в требования к API Gateway. | В мобильной сети запросы повторяются при обрывах связи и повторных нажатиях. Без защиты дубли записей станут регулярными, и каждый дубль превращается в обращение в кол-центр. |
| Синхронная цепочка «полис, запись, оплата, резерв анализов» без отката | Описание кейса (задание 3.2): у существующей синхронной цепочки вызовов нет механизмов отката при сбоях. SD-002: пациент оплатил, подтверждение не пришло, в логах ошибка «Booking not found» для paymentID. | Остаются частичные состояния: деньги списаны, а записи нет, или слот занят без оплаты. Их разбирают вручную, и с ростом числа записей ручной разбор перестаёт справляться. |
| 1С («Полисы») не выдерживает пиковую нагрузку, и её сбои выглядят как отказ по полису | INT-003 (Critical): проверка полиса падает с ошибкой 503 на пиках больше 50 rps. SD-008: 1С вернула null, пациенту показали «Полис недействителен», через пять минут повтор прошёл успешно. | Запись по ДМС останавливается на проверке полиса, а технический сбой 1С пациент видит как недействительный полис. Порог в 50 rps достигается уже сейчас, без приложения, а самозапись добавит нагрузку сверху. |
| Передача результатов анализов из LIS в CRM теряет, задерживает и дублирует данные | INT-002: загрузка через FTP падает с ошибкой 425, нужно ручное восстановление, задержка передачи в CRM до двух часов. SD-005: анализы, загруженные ночью, утром не видны в CRM, REST-коннектор не переотправил данные. INT-008: при сбое передачи XML-файлы дублируются, в CRM попадают дубли анализов. INT-011: LIS передал результат, а CRM не обновилась, сообщение застряло в очереди. | Не работает сценарий «получить результаты без звонка в клинику»: пациент не видит результат или видит дубль, звонит в кол-центр. Врач работает с неактуальными данными. |
| Очередь уведомлений переполняется на пиках | SD-006: пуш на Android не пришёл, очередь RabbitMQ переполнилась на пике. INT-004: лимиты RabbitMQ не задокументированы. | Подтверждения записи и сообщения о готовности анализов не доходят в вечерние часы пик, на которые рассчитан MVP. Пациент повторяет действие или звонит в клинику. |
| Уязвимости в системах с персональными и медицинскими данными | INT-006: SQL-инъекция в поле поиска пациента на веб-портале. SD-007: врач видит чужого пациента, возможна подмена сессии, тикет в работе. | Приложение открывает доступ к тем же данным из интернета и расширяет поверхность атаки. Утечка медицинских данных означает штрафы и потерю доверия пациентов. |
| Нет единой точки входа, rate limiting и документированных контрактов API | INT-010 (Critical): эпик на разработку API Gateway с rate limiting и идемпотентностью. Без версионирования изменения API ломают уже установленные приложения. |
| Нет сквозной трассировки запросов | INT-007 (Critical): нет distributed tracing, сложно найти корень сбоя. | Сценарий записи проходит через несколько систем, и сбой в нём ищется долго. Время восстановления растёт, что мешает цели доступности 99.95%. |
| Узкие места, которые не масштабируются добавлением экземпляров | INT-009: для базы расписания нужна реплика для чтения из-за блокировок. Описание кейса: число пациентов выросло на 40% за год, LIS и учёт полисов на 1С остались legacy. | Цель финального решения: 50 000 пользователей в пик и отклик меньше секунды для 99% запросов. Блокировки в базе расписания и legacy-системы ограничат рост раньше, чем будет достигнута эта нагрузка. |
| Нет единого интеграционного слоя, системы связаны напрямую по разным протоколам | Описание стека: SOAP и FTP в LIS, HTTP-шлюз к 1С, синхронный REST платёжного шлюза, RabbitMQ для уведомлений. В описании кейса: ИТ-системы развивались фрагментарно. | Для каждого сценария приложения интеграцию придётся собирать заново. Нет общих правил тайм-аутов, повторов и обработки ошибок, поэтому сбой одной системы непредсказуемо влияет на другие. |
