Целевая диаграмма: `target-c4.drawio` (рядом лежит `target-c4.png`). Ниже описаны только новые интеграции. Прямые вызовы веб-портала в расписание, платёжный шлюз, 1С, CRM и уведомления из диаграммы убраны: все обращения портала идут через API Gateway, чтобы у записи был один путь.

| Интеграция | Паттерн | Архитектурный стиль | Почему и как |
|---|---|---|---|
| Мобильное приложение → API Gateway | API Gateway; идемпотентный запрос (ключ Idempotency-Key в заголовке) | Синхронный запрос-ответ (REST поверх HTTPS) | Единая точка входа вместо прямых вызовов систем. Шлюз проверяет токен, применяет rate limiting, проверяет формат запроса и отсекает повтор запроса с тем же ключом, не пропуская его дальше. Это закрывает отсутствие шлюза и дубли от повторных нажатий и ретраев с телефона. |
| Веб-портал → API Gateway | API Gateway (замена прямых вызовов портала) | Синхронный запрос-ответ | Если бы мобильное приложение писало через оркестратор, а портал напрямую в расписание, два пути записи давали бы расхождения. Портал становится вторым клиентом шлюза с отдельными маршрутами, лимитами и ролями сотрудников. |
| API Gateway ↔ Сервис аутентификации | Делегированная аутентификация (OAuth 2.0 / OIDC), токен JWT | Синхронный запрос-ответ | Аутентификация вынесена из систем в отдельный сервис. Подпись токена шлюз проверяет сам, а в сервис ходит только за выпуском и обновлением токенов. Это уменьшает риск подмены сессии. |
| API Gateway → Расписание, Сервис полисов, Сервис анализов, CRM | Маршрутизация через шлюз | Синхронный запрос-ответ | Поиск врачей и слотов, чтение результатов, управление полисами и данные пациента для врача нужны пользователю сразу, поэтому это запросы, а не события. Приложение читает результаты из сервиса анализов, а не из CRM, и нагрузка пациентов на CRM не идёт. |
| API Gateway → Оркестратор записи | Saga (оркестрация); асинхронный запрос с ответом 202 Accepted | Комбинация: синхронный запрос-ответ на входе и асинхронная обработка внутри | Шлюз передаёт запрос синхронно, оркестратор сохраняет заявку и сразу отвечает 202 Accepted с идентификатором записи. Шаги выполняются в фоне. Приложение недолго ждёт итог и, если он пришёл, показывает его сразу, а иначе показывает «в обработке» и получает следующий статус (в том числе ссылку на оплату) запросом статуса или пушем. Так медленные 1С и платёжный шлюз не держат пользователя на экране. |
| Оркестратор → Расписание | Шаг саги с компенсацией; идемпотентный запрос; семантическая блокировка (слот «в резерве») | Синхронный запрос-ответ внутри асинхронной саги | Расписание остаётся существующим REST-сервисом и не читает команды из брокера, поэтому оркестратор вызывает его напрямую с ключом идемпотентности. Правило «на один слот одна запись» держится ограничением уникальности по идентификатору слота (врач и время начала) в БД расписания: ключ защищает от повтора одного запроса, ограничение защищает от разных запросов разных пациентов на один слот. Отмена слота служит компенсацией. |
| Оркестратор → Сервис полисов | Facade | Синхронный запрос-ответ | Следующий шаг записи ждёт результата проверки, поэтому событие не подходит. Сервис возвращает три исхода: «действителен», «недействителен», «неизвестно». Техническая ошибка 1С («неизвестно») не выдаётся пациенту как недействительный полис: запись приостанавливается с предложением повторить позже (параметры в Task4.1). |
| Сервис полисов → 1С | Anti-corruption layer; копия данных с периодической синхронизацией; Circuit Breaker на онлайн-вызовах | Комбинация: пакетная синхронизация по расписанию и синхронный запрос-ответ | 1С не выдерживает пики, зависает и меняет контракт без предупреждения: по словам разработчика интеграций, вместо JSON она стала возвращать XML. Сервис изолирует остальные системы от этих изменений и сбоев 1С. Проверки полиса идут по копии реестра полисов в базе сервиса, которую задание синхронизации раз в 5 минут обновляет изменениями из 1С. Онлайн в 1С сервис обращается, только если полиса нет в копии, и при прикреплении полиса, потому что мастер-системой полисов остаётся 1С. Подробно в Task4.1. |
| Оркестратор ↔ Брокер событий ↔ Платёжный сервис и Сервис анализов | Saga (оркестрация); команды и ответы через сообщения | Событийный, асинхронный обмен сообщениями; итоговая согласованность | Оплата и резерв анализов самые медленные и ненадёжные шаги, поэтому оркестратор не ждёт их в синхронном вызове: он отправляет команды и получает ответы событиями. Брокер для интеграционных событий отдельный от уведомлений: по словам DevOps-инженера, переполнение RabbitMQ на пике уже роняло уведомления (SD-006), а сервис уведомлений висит на том же RabbitMQ. Такой пик не должен задерживать команды саги. RabbitMQ оставлен, потому что он уже есть в компании. |
| Платёжный сервис ↔ Платёжный шлюз | Адаптер над шлюзом; идемпотентный платёж; сверка статуса (reconciliation) | Комбинация: синхронный запрос и асинхронный ответ | Платёжный сервис создаёт платёж синхронным REST-запросом. Идентификатор платежа задаёт наш сервис, и по нему можно запросить статус у шлюза; если шлюз принимает ключ идемпотентности, он передаётся с запросом. Шлюз возвращает ссылку на платёжную страницу, и оркестратор переводит запись в статус «ожидает оплаты». Тайм-аут не считается ошибкой: платёж остаётся в статусе «в обработке». Результат приходит вызовом шлюза (callback), а если не пришёл, сервис сам запрашивает у шлюза статус платежа. Оркестратору ответ отправляется только после итога. Это закрывает «деньги списаны, статус не зафиксирован» и двойное списание. |
| Мобильное приложение → Платёжный шлюз | Платёжная страница шлюза (hosted payment page) | Синхронный запрос-ответ (HTTPS) | Приложение получает ссылку на платёжную страницу в статусе записи и открывает её. Пациент вводит карту и проходит 3-D Secure на стороне шлюза, поэтому данные карты не попадают ни в приложение, ни в системы клиники. Итог оплаты шлюз сообщает платёжному сервису, а не приложению, чтобы статус платежа определялся только на сервере. |
| Сервис анализов → LIS | Адаптер над REST API LIS; идемпотентный запрос | Синхронный запрос-ответ | Резерв времени забора анализов приходит командой оркестратора, а у LIS уже есть REST API, поэтому сервис анализов вызывает его напрямую. Это шаг саги с компенсацией (снятие резерва). |
| LIS → Хранилище файлов → Сервис анализов | Claim Check; Event Notification; Idempotent Receiver | Комбинация: передача файлов и событийный обмен | LIS, как и сейчас, выгружает XML-файл результата в каталог на своём сервере, а агент выгрузки рядом с LIS загружает его в хранилище по S3 API вместо FTP-скрипта и повторяет загрузку до подтверждения. Объект записывается под ключом «идентификатор исследования и версия» только если ключа ещё нет, поэтому перезаписать результат нельзя; хеш содержимого служит проверкой целостности и отличает повтор от другого содержимого. Хранилище сообщает сервису анализов о новом файле. Сервис читает файл, отбрасывает дубль по ключу, сохраняет результат и публикует событие со ссылкой на файл. Исправление результата приходит как новая версия, старая сохраняется. Подробно в Task3.1. |
| Сервис анализов → Брокер → CRM и Уведомления | Publish / Subscribe; Idempotent Receiver | Событийный, асинхронный; итоговая согласованность | Сервис анализов не знает своих подписчиков. CRM получает результаты как обычный подписчик, без ручного коннектора, а новый подписчик добавляется без изменения публикующего сервиса. |
| Оркестратор → Брокер → Уведомления | Publish / Subscribe | Событийный, асинхронный | Статус записи уходит событием. Уведомление не должно задерживать запись, а ошибка отправки не должна откатывать её. |
| Уведомления → Мобильное приложение | Push-уведомление | Асинхронный | Приложение узнаёт о готовности записи или анализов без запросов по таймеру. |
