Для пагинации используются параметры limit и offset. Параметр limit задаёт размер страницы (по умолчанию 20, максимум 100; большее значение не проходит проверку схемы и отклоняется), offset задаёт, сколько записей пропустить от начала списка. Ответ содержит total, limit и offset, поэтому приложение понимает, есть ли следующая страница: она есть, пока offset + limit меньше total. Этот подход выбран, потому что список предстоящих записей одного пациента короткий и упорядочен по времени начала, поэтому offset прост в реализации и позволяет открыть любую страницу. Ограничение подхода: если между запросами страниц запись добавится или исчезнет, элементы могут сместиться, и запись окажется показанной дважды или пропущенной. Для короткого списка это приемлемо, а курсорная пагинация, которая этого избегает, здесь усложнила бы контракт без пользы.

Версия API указана в пути (`/api/v1/appointments`). Мобильные приложения обновляются не мгновенно, и у пользователей месяцами остаются старые сборки, поэтому несколько версий API должны работать одновременно. Версия в пути хорошо видна в логах и позволяет API Gateway направлять `/api/v1` и `/api/v2` на разные реализации. Совместимые изменения, например новое необязательное поле, остаются в v1, а несовместимые (удаление или переименование полей, смена типов) выходят как v2, при этом v1 продолжает работать, пока на нём остаются клиенты.
