Аутентификация построена на протоколе OAuth 2.0 с OpenID Connect по схеме Authorization Code с PKCE. Эту схему рекомендует для мобильных приложений RFC 8252: приложение не может хранить секрет клиента, поэтому код авторизации защищается проверочной парой code_verifier и code_challenge. Пациент входит не в самом приложении, а на странице сервиса аутентификации в системном браузере, и приложение никогда не видит его учётных данных. После входа приложение обменивает код авторизации на токены. Схема на `auth-scheme.png` (исходник `auth-scheme.md`).

Токены. Access-токен (JWT) живёт 15 минут и передаётся в каждом запросе в заголовке Authorization: Bearer по HTTPS, но не в адресе запроса и не в логах. В нём только идентификатор пациента, срок действия, назначение (audience) и права доступа, без персональных и медицинских данных. Refresh-токен живёт 30 дней и используется только для получения нового access-токена. При каждом обновлении выдаётся новый refresh-токен, а прежний аннулируется (ротация); если аннулированный токен предъявлен повторно, считается, что он украден, и вся цепочка токенов отзывается. Токены хранятся в защищённом хранилище телефона (Keychain на iOS, Keystore на Android).

Проверка на стороне системы. API Gateway проверяет подпись токена по публичным ключам сервиса аутентификации, срок действия и назначение. Идентификатор пациента берётся только из токена, а не из параметров запроса, поэтому нельзя запросить чужие данные, и короткий срок access-токена ограничивает ущерб от подмены сессии. Способ входа пациента (пароль, SMS-код и так далее) определяется сервисом аутентификации и на схему токенов не влияет.
